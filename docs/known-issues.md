# 알려진 구조적 이슈 및 개선안

## 1. 사용자를 "이름 문자열"로 식별하는 구조

### 현재 상태

근무표(`ShiftSchedule.MemberName`)를 비롯한 여러 테이블이 사용자를 **`User.Id` 가 아니라
`User.RealName` 문자열**로 참조한다. WPF 시절 구조를 그대로 이식한 결과다.

```
ShiftSchedule.MemberName  (string)  ──이름으로 매칭──▶  User.RealName
MaterialScheduleEntry.PersonName (string)
Dispatch / Handover 등의 담당자 필드도 동일
```

### 문제

| 상황 | 결과 |
|---|---|
| **동명이인** (예: 김철수 2명) | 두 사람의 근무·일정이 **한 사람으로 합쳐진다.** 한쪽에 도장을 찍으면 다른 사람 화면에도 나타난다. 현재 고유 인덱스가 `(MemberName, TargetDate)` 라서 **두 번째 동명이인은 아예 다른 근무를 저장할 수 없다.** |
| **이름 변경** (개명, 오타 수정) | 과거 근무·일정 기록이 **끊어져 조회되지 않는다.** 이전 이름의 데이터는 고아가 된다. |
| **퇴사자 이름 재사용** | 과거 퇴사자의 기록이 신규 입사자에게 붙을 수 있다. |

현재는 동명이인이 없어 겉으로 드러나지 않지만, **입사 시점에 조용히 데이터가 섞이는**
유형의 문제라 사전 대응이 필요하다.

### 개선안 (권장: 2단계, 데이터 이관 필요 → 별도 승인 후 진행)

**1단계 — 식별자 추가 (호환 유지)**
- `ShiftSchedule` 등에 `UserId` (nullable FK) 컬럼 추가.
- 기존 행은 이름으로 매칭해 `UserId` 를 채운다(동명이인은 수동 확인 목록으로 출력).
- 신규 저장은 `UserId` 와 `MemberName` 을 **함께** 기록한다.
- 조회는 `UserId` 가 있으면 그것을, 없으면 기존처럼 이름을 쓴다.

**2단계 — 전환 완료**
- 모든 행의 `UserId` 가 채워지면 고유 인덱스를 `(MemberName, TargetDate)` →
  `(UserId, TargetDate)` 로 교체.
- `MemberName` 은 표시용 캐시로만 남기고 식별에는 쓰지 않는다.

**임시 완화책 (2026-09-25 적용)**
- 계정을 만들거나 이름을 바꿀 때 다른 계정(퇴사자 포함)과 이름이 겹치면 **저장하지 않고**
  구분자를 붙이도록 안내한다(예: `김철수(B)`). 퇴사자 이름이면 "같은 사람이면 복직 처리" 를 안내한다.
  이미 겹쳐 있던 계정은 그대로 두며, 이름을 바꾸지 않는 수정은 막지 않는다(`UserService.EnsureNameFreeAsync`).
- 이름을 바꾸면 겹치는 계정이 없을 때만 근무표·교육 줄이 새 이름을 따라간다(`CarryNameChangeAsync`).

### 왜 지금 적용하지 않았나

스키마 변경 + 기존 운영 데이터 이관이 필요하고, 동명이인 매칭은 사람이 확인해야 하는
작업이라 **운영 데이터를 건드리는 결정은 별도 승인 대상**으로 판단했다.

## 2. 성적서 엑셀에 값을 써 넣는 일 — 웹에서는 아직 못 한다

### 현재 상태

성적서(엑셀)에 LOT 정보와 검사값을 채우고 특이사항 이미지를 넣는 일은 데스크톱판이
**Excel COM**(설치된 Excel 을 띄워 조종하는 방식)으로 한다. 서버에는 Excel 이 없고, 서버에서의
Office 자동화는 Microsoft 도 지원하지 않는다. 그래서 웹(포털·MES 웹판 모두)에서는 이 일을 못 한다.

| 하는 일 | 웹에서 |
|---|---|
| 성적서 파일 올리기 · 내려받기 | **된다** (파일을 그대로 주고받는다) |
| 성적서 양식(제품별 기본 파일) 지정 | **된다** |
| 런시트(공정 진행표) xlsx 만들기 | **된다** (ClosedXML 로 서버에서 만든다) |
| 성적서 칸에 LOT·검사값 채우기 | **안 된다** |
| 성적서에 특이사항 이미지 넣기 | **안 된다** |

### 왜 적어 두나

MES 웹판은 이 자리를 "아무 일도 하지 않고 성공을 돌려주는" 구현으로 채워 놨다. 그래서
특이사항 이미지를 올리면 **"삽입했습니다" 라고 답하지만 성적서에는 아무것도 들어가 있지 않았다.**
작업자는 넣었다고 믿고 넘어간다. 포털에서는 못 하는 일을 못 했다고 답하도록 바꿨다
(`UnsupportedCertificateExcelFiller`) — 안내 문구도 "데스크톱 프로그램에서 넣어 주세요" 로 바꿨다.

**데스크톱 프로그램을 내리기 전에 결정이 필요한 항목이다.** 고르자면 세 가지다.
1. 성적서 채우기는 계속 데스크톱에서 한다(웹은 조회·업로드만).
2. 서버에서 ClosedXML 로 다시 만든다 — 어느 칸에 무엇을 쓰는지(셀 좌표)가 데스크톱 쪽
   Certificate 프로젝트에 있고 **이 저장소에는 없다.** 그 매핑을 옮겨 와야 한다.
3. 윈도우 작업용 PC 한 대에 작은 워커를 두고 그쪽에 맡긴다.

## 3. 스키마를 맞추는 것은 마이그레이션이 아니라 SchemaUpgrader 다

`src/CleanPotal.Infrastructure/Data/Migrations` 는 2026-07 에서 멈춰 있고, 그 뒤에 모델에 생긴
컬럼(직급 · MES 권한 · 조직도 항목 …)은 마이그레이션에 들어 있지 않다. 일부러 그렇다 —
스키마를 실제로 맞추는 것은 `SchemaUpgrader`(없는 컬럼·테이블만 덧붙인다)이고, 운영(SQL Server)은
`EnsureCreated` + `SchemaUpgrader` 만 쓴다.

**시작할 때 `Migrate()` 는 어느 공급자에서도 부르지 않는다.** SQLite·SQL Server 모두
`DatabaseSchemaInitializer.Prepare` 가 `EnsureCreated` → 빠진 표 생성 → `SchemaUpgrader` → 빠진 컬럼 추가
순으로 **추가만** 한다(WPF 시절부터 이어진 SQLite DB 는 마이그레이션 이력과 실제 구조가 달라,
`Migrate()` 를 부르면 이미 있는 표를 다시 만들다 서버가 뜨지 않았다).
`Program.cs` 의 SQLite 등록에서 `PendingModelChangesWarning` 을 무시하는 것은 누가 `dotnet ef database update`
처럼 손으로 `Migrate()` 를 부를 때 EF 9+ 가 예외로 멈추지 않게 하려는 것뿐이다.

표를 새로 만들 때는 표와 그 인덱스를 한 트랜잭션으로 묶는다. 인덱스에서 실패하면 표도 되돌려
다음 실행에서 다시 시도한다(예전에는 표만 남아 "이미 있다" 로 보고 인덱스를 영영 만들지 않았다).

마이그레이션을 다시 만들어 맞추는 선택도 있지만, 그러면 **두 곳이 같은 일을 하게 된다.**
한쪽만 고치는 실수가 생기므로 지금은 한 곳(SchemaUpgrader)만 손본다.
(`MesEndpointAuthTests` 가 포털을 실제로 띄우므로, 이 자리가 다시 막히면 CI 가 잡는다.)

## 5. 테스트·CI

- `tests/CleanPotal.Tests` — 비밀번호 해시(WPF 구형 해시 호환·재해시·지문), 로그인
  (퇴사자 차단·비밀번호 변경), 로그인 시도 제한, 근무표 도장·조회 입력 검증에 대한
  회귀 테스트. SQLite 인메모리 DB를 써서 고유 인덱스 같은 제약도 실제로 검증한다.
  - 실행: `dotnet test`
- `.github/workflows/ci.yml` — 푸시·PR 마다 백엔드(복원·빌드·테스트)와
  프런트(타입검사·빌드·린트)를 돌린다. 취약 패키지 점검은 참고용으로 출력만 하고
  빌드를 실패시키지는 않는다.

- MES 배선·권한 회귀 테스트 (`MesModuleTests`, `MesEndpointPolicyTests`,
  `MesInspectionRowsTests`, `MesOperGateTests`, `MesPermissionCodesTests`).
  서비스 24종이 DI 에서 실제로 만들어지는지, MES 엔드포인트에 권한이 빠지지 않았는지,
  검사값 칸 판정·SPEC OUT 규칙이 그대로인지, MES 기준 데이터가 깔리고 두 번 불러도 늘어나지 않는지,
  OPER 실행 게이트(READ TIME · 레시피/설비 · 출고검사 NG · 출력 관리)가 그대로인지,
  포털에서 켜 준 MES 세부 권한이 실제로 통하는지와 코드 이름이 MES enum 과 어긋나지 않는지.

- 권한 판정 자체 (`DbPermissionHandlerTests`). 모든 API 가 지나는 한 곳이라 어긋나면 한 화면이
  아니라 전 영역이 함께 열리거나 닫힌다. 등급 0/1/2 의 조회·편집 구분, 퇴사자 차단(관리자여도),
  관리자 전용은 등급으로 열 수 없다는 것, 모르는 영역 이름은 막는다는 것, 등급 변경이 재로그인 없이
  반영된다는 것.
- 권한 변경 기록 (`MesPermissionAuditTests`) — MES 세부 권한을 켜고 끈 것이 한글 이름으로 남는지.

- 실제 HTTP 요청 (`MesEndpointAuthTests`, `AdminEndpointAuthTests`). 포털을 임시 SQLite 로 띄워
  로그인부터 한다. 권한 확인이 세 겹이 된다 — 정책이 **붙어 있는지**(`MesEndpointPolicyTests`, 반사),
  그 정책이 **무엇을 통과시키는지**(`DbPermissionHandlerTests`, 단위), 그리고 **이어 붙인 요청에서
  401/403 이 나오는지**(여기). 앞의 둘만으로는 인증·정책 배선이 끊겨도 전부 통과한다.
  사용자 관리 API(권한을 나눠 주는 자리)도 같은 방식으로 확인한다.
  - 이 테스트가 포털을 실제로 띄우므로, 시작 자체가 막히는 문제(예: SQLite 경로의
    `PendingModelChangesWarning`)도 여기서 드러난다 — 실제로 그렇게 한 번 잡았다.
